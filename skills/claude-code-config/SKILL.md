# Claude Code configuration (Nix-managed)

Everything under `~/.claude/` (and the mirrored `~/.codex/`, `~/.config/opencode/`)
is generated by home-manager from `~/src/system-config`. Edits made directly to
those files are either rejected (read-only store symlinks) or silently reverted on
the next rebuild, so persistent changes go in the repo and are applied with a
rebuild. Runtime-only tweaks (`/config`, `/effort`, "always allow") are fine for
the current machine but aren't the source of truth.

## Where things live

| What | Where |
|---|---|
| Option values for everything below | `modules/home-manager/default.nix` |
| Our extension module (`programs.claude-code-nix`: MCP, LSP, statusline, aliases, default model, mutable settings, HA mode) | `modules/home-manager/claude-code.nix` |
| Model tiers, delegation policy text, ponytail skills, Codex/OpenCode mirroring | `modules/home-manager/ai-models.nix` |
| Flox + Superpowers skills (`cullen.agenticSkills`) and exported module/profiles | `flake-modules/modules.nix` |
| Per-host toggles (e.g. HA mode) | `hosts/<host>/default.nix` |
| Custom skills / subagents | `skills/`, `agents/` (`commands/` holds only the vendored OpenSpec `/opsx:*` commands) |

The work laptop lives in a separate flake that imports this one's
`homeManagerModules.*`; per-device differences belong there or in `hosts/`, not
as conditionals in shared modules.

Upstream `programs.claude-code` (home-manager) supplies `settings`, `context`
(global CLAUDE.md), `skills`, `agents`, `commandsDir`, `hooks`/`hooksDir`,
`rules`, `outputStyles`, `plugins`, `marketplaces`, `mcpServers`, `lspServers`.
The option set moves with the pinned home-manager rev, so when in doubt read it
rather than guessing: `nix eval .#darwinConfigurations.cullens-MacBook-Pro.config.home-manager.users.cullen.programs.claude-code --apply builtins.attrNames`
(or grep the module in the locked home-manager source).

## Conventions that aren't obvious

- **MCP servers** go in `programs.claude-code-nix.mcpServers`, not the upstream
  option: upstream wraps the Nix binary, but the binary actually on PATH is the
  self-updating native install at `~/.local/bin/claude`. Ours merges into
  `~/.claude.json` at activation and is mirrored to Codex and OpenCode.
- **settings.json is mutable** (`mutableSettings = true`): activation deep-merges
  Nix-declared keys over the live file. A key declared in Nix wins on every
  rebuild; a key only ever set at runtime survives. "My setting keeps resetting"
  almost always means it's also declared in Nix.
- **The Claude Code binary is not Nix-managed** (`programs.claude-code.package`
  defaults to `null`); it updates itself. Only set a package to pin a version.
- **LSP servers** use absolute store paths (`"${pkgs.gopls}/bin/gopls"`) so they
  work regardless of PATH, and are never installed from the marketplace.
- **Plugins** are declared in `settings.enabledPlugins` (`"<plugin>@<marketplace>" = true`)
  plus `settings.extraKnownMarketplaces` for non-official marketplaces — not via
  `/plugin install`. Nix pins only the intent; Claude Code fetches the contents.
- **Skills** in `programs.claude-code.skills` are also linked into Codex and
  OpenCode, so write them harness-neutral (describe goals and commands, not
  Claude-only tool names, unless the skill is inherently Claude-specific). A
  value is a directory path or an inline SKILL.md string. To make one
  conditional, gate it the way `home-assistant` is gated
  (`// lib.optionalAttrs <flag> { … }`).
- **Slash commands are skills now.** A new user-invoked workflow is a skill
  with `disable-model-invocation: true`, which keeps its description out of
  the model's context. Don't add files to `commands/`.
- **Subagents** all go through `tieredAgent`, so frontmatter can say
  `model: @WEAK_MODEL@` / `@STRONG_MODEL@` and pick up `cullen.ai.models`.
  Note that `memory:` silently grants Read/Write/Edit, so leave it off
  read-only reviewers.
- **Global instructions** are `programs.claude-code.context` plus the rendered
  delegation policy; the same text becomes Codex's and OpenCode's `AGENTS.md`.
- **Default model** is `programs.claude-code-nix.defaultModel`, passed as
  `--model` by the shell aliases, so `/model` changes are session-only by design.

## Shapes that are easy to get wrong

Hooks use a matcher (tool-name pattern) plus a list of handlers:

```nix
programs.claude-code.settings.hooks.PreToolUse = [
  {
    matcher = "Bash";
    hooks = [ { type = "command"; command = "${myScript}/bin/check-bash"; } ];
  }
];
```

Permissions use the same rule syntax as the UI: `"Bash(git log:*)"`,
`"WebFetch(domain:example.com)"`, `"mcp__server__tool"`.

## Apply and verify

1. Build without switching to catch eval errors:
   `nix build .#darwinConfigurations.cullens-MacBook-Pro.system --no-link`
   (Linux / VM: `nix build .#homeConfigurations.<name>.activationPackage --no-link`).
2. Ask the user to run `nixswitch` (needs sudo; Linux: `nix run home-manager -- switch --flake .#<name>`).
3. Confirm the generated file changed as intended (`~/.claude/settings.json`,
   `~/.claude.json` for MCP, `~/.claude/skills/<name>/`) and note that new
   settings, skills, and MCP servers take effect in a new session.

## Looking things up

Claude Code changes weekly, so check current behavior instead of relying on
memory: `claude --help` for flags, the docs at
`https://code.claude.com/docs/en/<topic>` (settings, hooks, skills,
sub-agents, plugins, mcp, memory), and in Claude Code the built-in
`claude-code-guide` subagent for feature questions.
